# 0004. Инструменты: тонкие обёртки, 6 штук, описания на русском

Дата: 2026-10-31
Статус: принято

## Контекст

API Физикла проверен на проде (create → verify → delete). Полный набор из ~140 эндпоинтов избыточен; research предлагает минимальный набор + опции.

## Решение

Шесть инструментов, тонкие обёртки над API (сервер не принимает самостоятельных решений за LLM):

1. `search_food(query, limit=10)` → search v1 + гидратация карточек топ-N результатов (N ≤ 10, по умолчанию 10). Единственное сознательное отступление от «тонкой обёртки»: search возвращает только ID, и без карточек LLM тратила бы до 10 вызовов `get_food` на каждый поиск;
2. `get_food(id)` → карточка с порциями;
3. `log_food(serving_id, serving_amount, meal?, eaten_date?)` → `eaten-food/create-list`;
4. `get_day_summary(date?)` → итоги дня (`report/list/calendar`) + список записей (`eaten-food/list`) двумя секциями одного ответа;
5. `delete_eaten_food(id)` → `eaten-food/destroy`;
6. `list_meals()` → слаги приёмов.

Без `recognize_food_text` (LLM-распознавание текста) — consciously исключён: дневной лимит общий с приложением пользователя. Без `update_eaten_food`: правка = удалить и записать заново (расширение в будущем).

Имена инструментов/параметров — английские; описания (для LLM) и человекочитаемые поля ответов — русские: база продуктов русская, запросы вида «гречка», «творог 5%».

## Последствия

- Цепочка LLM: search → get → log; каждая запись прозрачна.
- В `get_food` подсвечиваем порцию «г» (`metric_weight: 1`) как способ записать «просто граммы».
- `log_food` шлёт массив из одного элемента (API принимает список — задел на будущее).
